# YouTube制作 AI社員チーム（28名）— 設計書

**状態: 下書き（ユーザー回答待ち）**

YouTubeチャンネル「AIでつくる、27歳の記録」（シリーズ「What If Lab」を含む）の動画制作を、28の役割（AI社員）に分けて進めるための設計書です。成果物は **長尺動画** と **Shorts**（長尺から切り出す派生Shortsが中心）です。

この設計は、ユーザーへの質問（1問ずつ）への回答を待つ間に用意した下書きです。ユーザーの回答で決まる値（ターゲット、トーン、NG表現、NGテーマ、目標値、投稿頻度、ツール、予算など）は、すべて **【未確定：ユーザー回答待ち】** と書いてあります。推測で値を埋めていません。

## 前提（変えないこと）

- **承認が必要な作業は実行前に確認する**（ユーザーのルール）。承認ゲートは G1 企画の承認／G2 台本の承認／G3 費用がかかる生成の前／G4 投稿の前 の4つ（`workflow.md`、`rules/approval.md`）。
- **公開は自動で行わない。** 初期値は「ユーザーがYouTube Studioで手動アップロード・公開」。
  - ユーザーの希望は「投稿まで任せたい」（Q1の回答）。そのため、ユーザーが YouTube Data API の利用設定（Google Cloud プロジェクトの作成、OAuth 同意画面の設定、認証）を行い、利用を承認した後は、R23 投稿管理が **「非公開」または「予約公開」でアップロード** するところまで行える設計にしています。**最終の公開は必ずG4でユーザーの承認を得ます。**
  - API の設定は済んでいる前提にしません。また、YouTube のポリシーにより「未確認（未監査）の API プロジェクトからのアップロードは非公開に制限される」場合があると言われていますが、**現時点では未確認**です。API を使い始める前に公式ドキュメントで確認します。
- 有料の生成（画像・動画・音声）、外部への送信、他者の著作物・実在の人物の肖像の使用は、実行前にユーザーの承認が必要です。
- 根拠のない数値・事実は作りません（`rules/fact_policy.md`）。

## 既存パイプラインとの関係

`what-if-youtube/` に、多くの役割をすでに実装したツールがあります（企画・調査・台本・絵コンテ・素材・ナレーション・編集・Shorts・サムネイル・品質検査・費用台帳）。また、制作状況と数値を記録する「YouTube制作台帳」（`what-if-youtube/apps/production-ledger/index.html`、claude.ai のアーティファクト＋データベース）があります。

- 各役割がどのファイルで実装済みかは `team.yaml` の `implemented_by` に書いてあります（無いものは「未実装」）。
- この設計書は既存ツールを変更しません。既存ツールのフォルダ `what-if-youtube/projects/<slug>/` と、この設計の `videos/<YYYYMMDD>_<slug>/` の対応づけ（同じにするか、片方に寄せるか）は **【未確定：ユーザー回答待ち】** です。

## フォルダ構成

```
youtube-team/
├── README.md              この説明
├── team.yaml              28役割の一覧（工程・上流/下流・承認の要否・既存実装）
├── workflow.md            工程の流れ・並行作業・成果物・承認ゲート・差し戻し先
├── overlaps.md            担当が重なりやすい役割の境界と引き継ぎ点
├── questions.md           ユーザーにまだ聞く質問（1問ずつ）
├── intake/
│   └── video_request.md   「動画を1本作って」「Shortsを1本作って」の受付チェックリストとブリーフ
├── roles/                 R01〜R28 の業務手順書（1役割1ファイル）
├── rules/                 ユーザーの条件を書くルール（更新していくもの）
│   ├── account.md           チャンネル概要・ジャンル・ターゲット・目的
│   ├── tone_and_structure.md 参考台本のトーンと構成
│   ├── ng_expressions.md    使ってはいけない表現
│   ├── ng_topics.md         企画のNG条件
│   ├── metrics.md           確認する指標と目標
│   ├── approval.md          承認が必要な作業
│   └── fact_policy.md       事実・数値・出典の扱い
└── skills/                繰り返し使う手順（Claude Code のスキル形式）
    ├── video-intake.md
    ├── hook-writing.md
    ├── fact-check.md
    ├── weekly-analytics-review.md
    └── rule-update.md
```

動画1本ごとの作業フォルダ（まだ作っていません）: `videos/<YYYYMMDD>_<slug>/`。中身は `workflow.md` の「成果物」表を参照。週次の分析は `analytics/weekly/<YYYY-WW>/`、採用された改善提案は `improve/` に置く想定です。

## ルールの更新方法

ユーザーが新しい条件を言ったら（例:「〇〇という言葉は使わないで」）、`skills/rule-update.md` の手順で更新します。

1. どのルールファイルに入る条件かを決める（表現→`ng_expressions.md`、テーマ→`ng_topics.md`、数値目標→`metrics.md` など）。
2. 該当の欄に、ユーザーの言葉をできるだけそのまま書く（解釈を足す場合は「解釈」と分けて書く）。
3. ファイル先頭の「最終更新」と、末尾の「変更履歴」の表に1行追加する。
4. 影響を受ける役割（roles/）を `team.yaml` から探し、必要なら手順を直す。
5. 更新内容をユーザーに1〜3行で報告する。

ルールの変更（特にR27改善提案からの変更）は、ユーザーの承認を得てから書き込みます。
